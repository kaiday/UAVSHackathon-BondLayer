What is real, and what is simulated

A hackathon demo that does not say which parts are mocked is asking to be taken on trust. Here is the honest version.

We are not building an agent

In a room full of agents, we are building the thing agents read. BondLayer is a merchant-side UCP server plus a signed extension. It holds no state per shopper, makes no decision, and returns the same published facts to every caller.

That is a position, not a limitation. A publishing layer has:

  • No per-comparison latency budget. Nothing has to be decided while a shopper waits.
  • No real-time dependency at the moment of decision — the merchant can be offline and its published, signed facts still stand.
  • No privacy story to defend, because the merchant never learns it was compared. There is no shopper data to leak, because none arrives.

The optional agent-side valuation library is a separate thing, and the headline demo deliberately does not depend on it — assuming agents adopt our library would assume away the problem.

“So what does it decide?”

Nothing, by design. The version that decides is designed and deliberately deferred: org.bondlayer.retention_request, where a merchant that is losing answers with a bounded, signed, expiring counter-offer within margin floors.

We cut it because deciding at comparison time buys a second protocol flow with a latency budget, a merchant-side policy engine, a privacy surface we currently do not have, and Australia's automated-decision transparency obligations, which commence 10 December 2026. It is roughly as much work as everything else combined.

Designed, costed, deferred on purpose — docs/deferred-retention-engine.md

The one place we do use an agent

Merchant onboarding. An LLM drafts typed benefit records from the merchant's prose policy document — and a person approves before anything is signed. Agent where it is cheap and reversible; never in the serving path.

The actual HTTP, both ways

Three merchants, each a separate service on its own port, spoken to over real HTTP — not in-process calls, which would assume away the thing being demonstrated. The only difference between these two columns is the UCP-Agent header.

UCP conformance

Run against the live services every time this page loads, and again by pytest tests/test_ucp_conformance.py. A second test deliberately breaks the namespace to prove these checks can go red — a suite that cannot fail is decoration, and this one is evidence.

Every system prompt, verbatim

The demo claims a third-party agent chose on merit. That is worth nothing unless you can read what the agent was told.

The prompt did not always work — and we did not rig it

The first recorded run put six signed benefits in front of the model and it ranked on list price anyway, picking Peak in both conditions. Two causes: three benefits carried no dollar figure, so they read as feature bullets; and the prompt never asked for effective cost.

We fixed the data and asked for total cost — which is what any competent shopping agent is told to do — and narrowed the claim rather than naming ourselves in the prompt:

Publishing signed, priced, structured data does not make a price-ranking agent change its mind. It makes an agent that is already reasoning about total cost able to credit you for what you actually offer — and denies that credit to competitors who publish nothing, or publish it unsigned.

Is the comparison rigged?

The fair objection: Alpine wins because we gave Alpine benefits and its competitors none. So we gave the competitors real policies too. Every merchant below offers genuine, competitive terms, published for humans. The difference on the wire is whether an agent can read them, and whether the merchant can prove them.

Same code, all three

Every merchant is an instance of the same MerchantService, rendered by the same _render(), negotiated by the same negotiate(). There is no per-merchant branch anywhere. Two conformance checks assert this, and you can read the responses on The wire.
